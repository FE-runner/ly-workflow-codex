# Lyx Ponytail

> 基于 Ponytail（MIT）的最小完整范围原则，按 lyx 流程边界改写。

> 调用方式：`@lyx-ponytail [lite|full|ultra|off]`；工作流内部按阶段加载，默认使用 `full`。

用于 lyx 的方案、实施和审查阶段。目标是用**最小完整改动**解决用户问题，同时保留流程要求的验证、安全、错误处理和范围检查。

## 流程优先级

- 用户明确要求、项目 `AGENTS.md` / `CLAUDE.md`、`testMode`、审查分级、提交和范围纪律优先于本 skill。
- 不得以“更简单”为由跳过必要测试、类型检查、错误处理、权限校验、安全、可访问性或迁移。
- 本 skill 只收窄方案和实现范围；不替代 lyx 的审查、裁决或归档门禁。

## 最小完整范围

按以下顺序选择方案：

1. 这项能力是否真的需要存在？不做用户未要求的功能、选项、扩展点和“以后可能用”的抽象。
2. 代码库已有 helper、组件、服务或约定时，优先复用现有模式。
3. 标准库、平台能力或已安装依赖足够时，不新增依赖或包装层。
4. 能一眼读懂的一行实现优先于难读的短写法；可读性不是行数比赛。
5. 其余情况使用满足需求的最小实现。

每次改动前先盘点它必须触达的位置：调用方、测试、fixture、配置、导出和文档。额外功能不属于 scope。

## 实施约束

- 删除优先于新增；不引入没有当前使用者的抽象。
- 保持项目已有的分层、命名、错误处理和目录结构。
- 修 bug 先搜索受影响的调用方，尽量在共享根因处修一次。
- 移动或合并代码时保留既有校验、错误处理和边界行为。
- 用户未要求的重构、格式化、配置项和兼容层不顺手加入。
- 真正省略某项能力时，用一句话说明边界；不要把它扩成新的 Requirement 或 task。

## 验证

- 新分支、循环、解析、金额、安全或脚本等非平凡逻辑，需要相称的测试或可执行自检。
- 纯机械、无行为变化的改动可复用既有验证，但仍须满足项目门禁。
- 有已知限制的捷径用一行注释写明：`shortcut: <限制>，<何时升级>`。

## 输出

完成阶段报告时，用一到两行说明主动省略了什么、未检查什么，以及用户需要知道的风险。

## 档位

- `lite`：只做用户要求，指出一个更小选项。
- `full`：默认，执行上述规则。
- `ultra`：在实施前质疑需求中不能证明必要的部分。
