# Lyx Code Simplification

> 参考 Claude Code Simplifier 的行为不变原则，按 lyx 流程边界改写。

> 调用方式：`@lyx-code-simplification`；由 lyx 实施或代码审查阶段内部加载。

用于功能或修复行为稳定之后、进入自审或代码审查之前。目标是让本次 diff 更容易阅读、理解和维护，而不是机械减少行数。

## 适用边界

- 只处理本次 change 已改文件；不顺手整理范围外代码。
- 不理解代码职责、调用方、错误路径和既有测试时，不得删除或合并。
- 性能关键路径若“简化”会更慢，保留原实现。
- 准备整体重写的临时代码不投入简化。
- 本次 diff 已清晰且没有具体收益时，不制造改动。

## 必须保持

每次简化前逐项确认：

- 所有输入和输出不变。
- 错误类型、错误信息、错误路径和失败时机不变。
- 副作用、调用顺序、事务边界和并发行为不变。
- 既有测试语义不变；不得修改测试来迁就简化。
- 命名、导入、错误处理和类型标注遵循项目既有约定。

无法确认行为等价时，不做该简化。

## 具体信号

- 三层以上嵌套：用 guard clause 或具名 helper 降低理解成本。
- 长函数承担多个职责：只在能形成清晰职责边界时拆分。
- 重复条件或重复逻辑：提取项目已有的 predicate / helper。
- 不可达分支、未使用变量、无价值 wrapper：确认无调用方后删除。
- 嵌套三元链、晦涩 reduce 或标志参数：改为显式分支、查找表或有名步骤。
- 误导性名称：按项目约定改为描述实际行为。

## 执行纪律

- 一次只做一类简化，保持 diff 可审查。
- 先理解 Chesterton's Fence：不清楚某段代码为何存在时，先读调用方、测试和 git 历史。
- 不把两个无关函数合并成更难理解的函数。
- 不为减少行数牺牲错误处理、校验、可访问性或可调试性。
- 不在审查循环内运行测试或类型检查；慢验证仍由当前 workflow 的阶段门禁负责。
- 简化改动代码后，按当前阶段要求重跑受影响验证；不新增独立 refactor commit。

## 完成检查

- diff 只包含本次 change 范围。
- 既有测试无需修改仍表达原行为。
- 没有删除错误处理、安全校验或边界判断。
- 简化后的版本比原版更容易理解和审查；否则回退该简化。
