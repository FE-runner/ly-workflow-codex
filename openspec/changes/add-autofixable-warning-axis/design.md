## Context

- 现状（见 `proposal.md` - Why）：审查-修复循环只消费 Critical；Warning 一律在循环结束后按节写入 `openspec/changes/<change-name>/review-findings.md` 快照，仅当同一会话内用户点名才会修。
- 判级标准的落点已经固定：六处 `## 判级标准`（`templates/hosts/codex/prompts/reviewer.md`、`plan-reviewer.md`、`templates/hosts/claude/agents/lyx-reviewer.md`、`lyx-plan-reviewer.md`、`templates/skills/review-code.md`、`review-plan.md`）必须逐字一致，由 `src/utils/__tests__/host-adapters.test.ts` 的三方一致性断言守护。新轴的判据必须落在同一处——`reviewExecutor = "main"` 路径不读角色词，只读共享模板。
- 循环的既有耗散控制：熔断、驳回硬线、无法安全自动修复、修复后验证失败、审查调用失败、全局轮数上限（默认 5 轮）与"清零优先于轮数上限"。
- 实测基线：本仓库 19 个审查修复 commit 的轮数分布为 1 轮 ×3、2 轮 ×5、3 轮 ×6、4 轮 ×1，从未触及 5 轮上限；7 份归档快照共 22 条 Warning，其中 16 条符合"目标唯一 / 不新造决策 / 改法机械 / 可验证"，6 条含需要拍板的分支。

## Goals / Non-Goals

**Goals:**

- 让机械性 Warning 在循环内顺手修掉，同时把"需要人拍板"的 Warning 留在快照里。
- 让新增机制对循环轮数的影响**可证明有界**，不引入新的"永远差一条"失效模式。
- 判据在 `main` 与 `subagent` 两条执行者路径下完全一致。

**Non-Goals:**

- 不扩大 Critical 的范围（严重度与"可否机械修复"是两根轴，见 Decisions）。
- 不改熔断、驳回硬线、无法安全自动修复、验证失败与审查调用失败这些既有终止条件的语义。
- 不改 `reviewMode` 门控、`@lyx-apply` 实施流程、`@lyx-archive` 归档前完整验证。
- 不引入新的配置字段与状态字段（快照仍不承载 open/closed 状态）。

## Decisions

**D1：新增一根正交轴，而不是抬高 Critical 阈值。**
严重度回答"不修会发生什么"，"可自动修复"回答"能不能机械地修"，两者正交：存在严重但需要决策的条目（改公开契约、依赖产品口径），也存在轻微但完全机械的条目（文案键漏一侧、漏同步）。放宽 Critical 会让阻塞项膨胀，并同步抬高熔断与驳回硬线的触发率。
备选（已否决）：把"机械可修"并入 Critical 判据——会把门当队列用，且无法表达"严重但不可自动修"。

**D2：标注只加在 Warning 上。**
Critical 无论可否自动修都进循环（不可安全修的由既有终止条件 3 停下）；Info 不参与循环也不入快照。给 Critical 加同一字段只会产生一个无人消费的取值。

**D3：标注由审查者产出，当前会话可覆盖且必须留痕。**
审查者更贴近发现现场，`main` 路径下只有一个主体，成本最低。允许覆盖是因为判据必然存在灰区；禁止静默覆盖（必须在报告列出原标注、覆盖后取值与理由）是防止覆盖权变成规避手段。备选（已否决）：只允许「是」→「否」单向覆盖——同样需要留痕，双向允许不增加风险面，却避免"审查者漏标「是」后无法补救"。

**D4：自动修只消费第 1 轮。**
若允许每一轮都消费新出现的机械性条目，等于给一个"生产成本极低、判据带模糊性"的类别开了无限供给：审查者再审一遍同一批文件，总能再找出两条措辞或同步问题，清零条件会变成永远差一条。限定首轮后，"修完又出新"的尾巴被物理切断。
备选（已否决）：只在前 N 轮消费新出现的条目——需要额外追踪"哪些是新出现的"，且仍然留下尾巴。

**D5：首轮条目修不好即降级，不中断流程。**
某条首轮「是」条目在紧接的下一轮仍被判定存在时，降级为「否」并落快照、退出清零判定。理由是低严重度条目不值得升级成人工介入；判同键直接复用熔断的三元组（文件路径 + 问题类别 + 定位锚点），不新造身份识别。
备选（已否决）：对「是」条目也套用熔断（停止整个循环）——会把一条文案级别的分歧升级成全流程阻断。

**D6：熔断与驳回硬线仍以 Critical 为唯一判定对象。**
这两个条件是为"主会话与审查者的判断分歧"设计的高成本刹车；把 Warning 级分歧纳入会显著提高人工介入率，而 Warning 分歧的代价低——落快照即可。

**D7：由「只消费首轮」与「降级不返工」两条规则共同推出轮数上界：自动修最多让循环多跑 1 轮。**
仅当"首轮 Critical 数为 0 且存在「是」条目"时才会比现状多一轮（那一轮用来验证首轮条目）；首轮已有 Critical 时，多出的自动修工作量搭同一趟车，零额外轮数。全局 5 轮上限与"清零优先"不变。

**D8：判据落在六处 `## 判级标准`，沿用既有三方一致性断言。**
`main` 路径只读共享模板，`subagent` 路径读角色词；两侧必须拿到同一份判据，因此新增内容同样要求三处逐字一致。备选（已否决）：只在角色词里写——`main`（默认）路径拿不到判据，会出现"声明了但没人读"的半截状态。

**D9：快照口径从"只收 Warning"改为"只收未被自动修复的 Warning"。**
这与 `review-findings-snapshot` 主 spec 里既有的"每节 SHALL 记录该审查类型最近一轮未被自动修复的发现"一致——该措辞此前是空转的（循环只吃 Critical），本次把它变成实际规则。因为已修的「是」条目随统一 commit 落库、不进快照，`@lyx-archive` 的归档前核对与 `@lyx-explore` 的未解决计数都基于"快照里没有解决子项的 Warning"，口径天然兼容，预期零改动。
备选（已否决）：把「是」条目也留在快照里再标注已修——会让归档前核对反复询问已自动完成的条目。

**D10：首轮「是」条目的逐字原文进入第 2 轮 TASK。**
非 fork spawn 无历史记忆，"这条到底修没修好"只能靠原文 + 路径清单判定；不传原文则无法区分"已修复"与"本轮新出现"。

## Risks / Trade-offs

- **判级漂移从"严重度"迁移到"可自动修"** → 判据写死四条并列负面信号 + 反向清单（必须判「是」的四类）+ 多子问题整条判级；当前会话覆盖必须在报告逐条留痕，可事后审计。
- **审查者方差导致次轮冒出新的机械性条目**（历史上出现过"首轮 0 Critical、次轮 3 Critical"） → 只消费首轮：新出现的一律落快照，不再循环。
- **首轮「是」条目修不干净** → 一次机会后降级，SHALL NOT 返工，避免"清零永远差一条"。
- **轮数上升** → 上界 +1 轮，且只在首轮零 Critical 且有「是」条目时发生；5 轮上限、清零优先、熔断与驳回硬线均不变。若实测出现"每轮都冒新条目"，说明判据过松，应回收判据而非放宽轮数。
- **`--no-commit` 与统一 commit 失败场景** → 已修但未落库的「是」条目按既有规则进入快照并记录基线状态；SHALL NOT 为快照补建 commit。
- **六处文本重复的维护成本** → 由现有三方一致性断言守护（本次扩到覆盖新判据）；任一处分叉即测试失败。
- **历史快照兼容** → 读取口径不变（仍按"顶层条目下无 `- 解决：` 子项即未解决"判定）；本 change 不改快照结构、编号与归档回写规则。
- **已安装副本不会自动生效** → 本 change 只改仓库内模板；已装 skill 与角色词需 `lycx update`（或下次发版）重渲染后生效。

## Migration Plan

- 纯模板 / 文档 + 断言改动，无数据迁移、无配置字段新增、无 schema 变更。
- 生效顺序：合并后由用户执行 `lycx update`（或等下一次发版）重渲染 skill 与角色词；未更新的副本继续按旧行为（Warning 一律落快照）运行，两版之间无中间态冲突。
- 回滚：还原六处判级标准与 `review-code.md` / `review-plan.md` / `propose.md`，并还原 `review-findings-snapshot` 的收录口径即可；无需回滚数据。
