# context.md — add-autofixable-warning-axis

软上下文：只记 artifact 之外的讨论结论、否决理由与已知坑。判据与规则的规范文本见 proposal/design 与两份 delta spec，此处不重复。

## 关键决策与理由

1. **不扩 Critical，改为给 Warning 加一根正交轴。** 严重度回答"不修会发生什么"，"可自动修复"回答"能不能机械地修"，两者正交。依据：本仓库 7 份归档快照共 22 条 Warning，其中 16 条属"目标唯一 / 不新造决策 / 改法机械 / 可验证"。
2. **标注只加在 Warning 上。** 不可安全自动修的 Critical 已有终止条件 3 兜底；Info 既不进循环也不入快照。给 Critical 加同一字段会产生一个无人消费的取值。
3. **自动修只消费第 1 轮 + 未修好即降级。** 机械性条目"生产成本极低"，若每轮都消费新出现的，清零条件会永远差一条。这条约束把该机制对轮数的影响压到"最多 +1 轮"。
4. **熔断与驳回硬线仍只以 Critical 为判定对象。** 它们是为"主会话 vs 审查者判断分歧"设计的高成本刹车；把 Warning 级分歧纳入会显著抬高人工介入率，而 Warning 分歧落快照即可。
5. **判据落在六处 `## 判级标准`（4 份角色词 + 2 份共享模板）。** `reviewExecutor = "main"` 路径不读角色词、只读共享模板，判据只写角色词会造成"声明了但没人读"。

## 已否决的备选

- **把"机械可修"并入 Critical 判据**：等于把门当队列用，且无法表达"严重但不可自动修"。
- **每轮都消费新出现的「是」条目 / 只在前 N 轮消费**：前者留下"修完又出新"的尾巴；后者需要额外追踪"哪些是新出现的"状态，尾巴仍在。
- **对「是」条目套用熔断（停止整个循环）**：会把一条文案级别的分歧升级成全流程阻断。
- **让「是」条目也留在快照并标注"已自动修复"**：归档前核对会对已完成的条目反复询问。
- **只在角色词里写判据、不进共享模板**：`main`（默认）路径拿不到判据。

## 范围边界

- **做**：新增标注契约与判据、正常清零定义扩展、首轮限定与降级规则、TASK 增量原文、空 commit 判据修正、快照收录口径与节移除判据。
- **不做**：不改 `reviewMode` 门控、`@lyx-apply` 实施流程、`@lyx-archive` 归档前完整验证；不加配置字段；不改快照结构、连续编号、归档回写与 `@lyx-explore` 展示口径。
- `templates/skills/archive.md` 与 `explore.md` 预期零改动：两者都基于"快照里没有解决子项的 Warning"，而已修的「是」条目随统一 commit 落库、不进快照。tasks 4.2/4.3 要求实测核对并加断言守护。

## 已知坑

- **MODIFIED 必须整块复制且 Scenario 名不可改**：`openspec validate` 会以"omits scenario(s) the current spec still has"拒绝改名。本次已在 `review-findings-snapshot` 上踩过一次（改名两个 Scenario 被拒），修法是保留原名、只改 THEN 内容。
- **六处判据文本重复**：任何一处单独修改都会打破三方一致性；既有断言（`host-adapters.test.ts`）自动覆盖，改动时要同步六处。
- **`--no-commit` 与统一 commit 失败场景**：已修但未落库的「是」条目仍进快照，并在元信息里如实记录基线状态。
- **生效方式**：本 change 只改仓库内模板；已装 skill 与角色词需 `lycx update`（或下次发版）重渲染后生效，两版之间无中间态冲突。
- **判级灰区在两个轴之间迁移**：本 change 把灰区从"严重度"搬到"可否机械修"，因此附带负面信号、"推荐方向例外"与"必须判「是」的反向清单"三件套；若实测出现"每轮都冒新的「是」条目"，应回收判据而不是放宽轮数。
