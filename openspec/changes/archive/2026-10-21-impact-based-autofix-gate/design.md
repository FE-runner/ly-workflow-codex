## Context

- 现状（见 `proposal.md` - Why）：v0.10.0 用轮次决定自动修消费范围——只修首轮、次轮新增落快照、首轮未修好降级。它给出"最多 +1 轮"的硬上界，但把重要性与出现顺序绑死。
- 既有两根轴：严重度（Critical / Warning / Info）与 `可自动修复`（是 / 否）。本轮新增第三根轴 `影响落地`。
- 终止条件现状：熔断、驳回硬线、无法安全修复、验证失败、调用失败、系统性误判、5 轮上限；全部只以 Critical 为判定对象。
- 快照口径现状：只收录"未被自动修复的 Warning"（v0.10.0 起）。

## Goals / Non-Goals

**Goals:**

- 让"不修就会挡路"的 Warning 无论出现在第几轮都进入修复；让"不挡路"的 Warning 不再占用循环。
- 用语义收敛替代轮次收敛：影响项必须有结论（修完或停下），不影响项永不拖住循环。
- 保住轮数上界：任意一轮新增影响项都受两条刹车约束，仍受 5 轮兜底。

**Non-Goals:**

- 不改严重度分级与 Critical 的判定标准。
- 不改 `可自动修复` 的判据。
- 不改快照结构、编号、归档回写与 `@lyx-explore` 展示口径。
- 不新增配置字段。

## Decisions

**D1：新增 `影响落地` 轴，而不是继续调轮次。**
轮次回答"什么时候出现"，影响面回答"该不该挡路"。前者是过程属性，后者是结果属性，只有后者能稳定区分"必须修"与"可以留"。
备选（已否决）：把首轮放宽到前 N 轮——仍是过程属性，只是把任意边界往后挪，N 大了重新出现"修完又出新"的尾巴。

**D2：`review-plan` 解读为"影响实施"，`review-code` 解读为"影响本次交付"。**
方案审查在实施前，"不修会改变 tasks / 接口 / 验收"成立；代码审查在实施后，等价问题是"不修会导致交付物不满足 change 目标、验收不过或引入回归"。字段名统一为 `影响落地`，判据文本写成同时覆盖两者的表述，保证六处逐字一致。

**D3：四象限消费，`可自动修复=否 + 影响落地=是` 直接停止。**
这格是本次设计的核心：一条会挡路但修不了的条目，落快照后继续执行等于假装处理过。停止转人工是唯一诚实的选择。备选（已否决）：落快照后继续——会让"留痕"被误当成"已处置"。

**D4：删除「只消费首轮」与「未修好即降级」。**
降级规则的前提是"低严重度条目不值得挡路"，但影响项恰恰不能降级；不影响项又本来就落快照、不需要降级。两条规则在新判据下都失去意义，保留只会制造歧义。

**D5：三条收敛刹车替代 +1 轮上界。**
（a）同一影响项相邻两轮仍在 → 停止：影响项不接受"修了没修好"的静默放行；（b）第 3 轮起新增影响项 → 停止：修到第三轮还有新的挡路问题，说明方案本身不稳定；（c）5 轮全局上限不变。三条叠加后，影响项最多消耗两轮就会要么清零要么停止，不存在无限尾巴。

**D6：快照口径零改动。**
四象限下：`是+是` 修完不入快照；其余三种（`是+否`、`否+是`、`否+否`）都未被自动修复 → 都入快照。现有"只收未被自动修复的 Warning"天然覆盖，`review-findings-snapshot` 不需要改。

**D7：标注由审查者产出、主会话可双向覆盖并留痕。**
与 `可自动修复` 完全同构，复用同一套覆盖与留痕规则，不引入新的仲裁机制。

**D8：判据落在六处 `## 判级标准`。**
`reviewExecutor = "main"` 不读角色词，只读共享模板；两族文本保持逐字一致，由既有三方断言守护。

## Risks / Trade-offs

- **影响判定主观** → 四条判据（改变实施方式 / 交付结果 / 验收标准 / 引入回归）+ "必须判是"与"必须判否"双向清单 + 覆盖留痕；判错可事后审计。
- **影响项判定过宽导致频繁停止** → "必须判否"清单明确把纯措辞、排版、术语统一、可读性偏好挡在外面。
- **轮数上升** → 三条刹车 + 5 轮兜底；新增影响项从第 3 轮起直接停止，不允许无限追加。
- **六处文本重复** → 既有三方一致性断言；本轮扩展断言覆盖 `影响落地` 锚点。
- **历史快照兼容** → 读取口径不变（无 `- 解决：` 子项即未解决）；本 change 不改快照结构。
- **已装副本未生效** → 纯模板改动，需 `lycx update` 或下次发版；两版之间无中间态冲突。

## Migration Plan

- 纯模板 / spec / 文档 + 断言改动，无数据迁移、无配置字段、无 schema 变更。
- 生效顺序：合并后 `lycx update`（或发版）重渲染；未更新的副本继续按 v0.10.0 的轮次制运行。
- 回滚：还原六处判级标准、两份 review 模板、`propose.md` 与两份主 spec 即可。
