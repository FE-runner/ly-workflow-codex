## Context

当前执行模型把审查与实施固定为"spawn 独立 subagent"，主 agent 只作为环境不可用时的回退路径。设计与实测之间存在两处偏差。

一是 spawn 可用性不可靠。实测同一 app 版本（`0.155.0-alpha.2.6`）、同一模型与 provider 下，不同会话的工具注册形式不同：一个会话把 `multi_agent_v1` 注册为独立 namespace 并能成功 spawn，另一个会话把它包进 `mcp__tools__` 聚合层，调用直接返回 `unsupported call`。也就是说"独立审查"这个默认承诺在部分会话下并不成立，而流程仍按"有独立审查"的口径产出报告。

二是子代理跨轮复用被误判为不可行。模板明确写着"子 agent 会话随主会话回合结构而存在，回合结束即失去访问能力"，据此要求每轮重新 spawn。实测证明该假设不成立：子代理首次任务完成后再用 `send_input` 唤醒仍能收到响应，且保留自身会话上下文。

此外，测试 / 类型检查 / 构建目前在审查循环每轮执行一次，是耗时的主要来源之一。动机与范围见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 让"谁执行审查/实施"成为显式可配置项，主 agent 为默认执行者。
- 主 agent 路径去掉为"两个主体互相制衡"设计的机制（逐条裁决、驳回硬线、熔断），把循环化简为"自审 → 修复 → 自查确认"。
- 子代理路径保留既有严格循环，但默认复用同一子代理，复用失败才重新 spawn。
- 把测试 / 类型检查 / 构建从审查循环移到归档前一次完整验证。
- 移除两个已弃用字段，消除"字段保留但不读取"的长期负担。

**Non-Goals:**

- 不重构自动模式的中断处理策略（7 类终止条件的"分级继续"）。本次只做执行者切换与验证时机调整，"容易中断"这一症状仅被部分缓解。
- 不优化串行流水线的并行度，也不调整模型与推理档的选取策略。
- 不改变审查范围判定、基线锚定、Critical / Warning / Info 分级这些与执行者无关的规则。

## Decisions

### 1. 用显式执行者字段，而不是复用模型字段的"留空"语义

新增 `[codexHost] reviewExecutor` / `codingExecutor`，取值 `"main"` / `"subagent"`。

备选方案是"模型字段留空 = 主 agent 执行，配置模型 = spawn 子代理"。它更简洁，但会把"执行者"和"用什么模型"两个正交维度压进一个字段，并且无法表达"spawn 子代理但继承当前会话模型"这个组合。项目已有的字段风格（`reviewModel` / `codingModel` 与推理档一一对应）也支持拆开表达。

### 2. 默认值是 main，且接受破坏性变更

未配置执行者字段等价 `"main"`。这意味着升级用户即使不改配置，行为也会从"spawn 子代理"变为"主 agent 直接执行"。

备选方案是默认 `"subagent"` 以保持向后兼容。放弃的理由是：spawn 可用性实测不可靠，把默认值押在一个不稳定的能力上会持续制造"表面独立审查、实际回退"的假象；同时用户明确选择不做兼容。代价必须在 CHANGELOG 与迁移说明中写清楚。

### 3. 主 agent 路径不做逐条裁决，也不设驳回硬线

逐条裁决、驳回硬线、熔断、审查对象类型持续系统性误判这四类机制的设计前提是"审查发现"与"主会话裁决"是两个主体。执行者为 `main` 时主体合并，这些机制失去意义。

主 agent 路径改为：直接产出分级发现 → 修复 Critical → 再自查一轮确认清零，最多 2 轮。超过 2 轮仍非清零则停止转人工。保留"分级输出"是因为它的价值不依赖主体分离——它仍是给人看的结构化结果。

### 4. 子代理路径默认复用同一子代理

首轮 spawn 之后，后续轮次用 `send_input` 复用同一子代理；复用失败（会话丢失、`send_input` / `resume_agent` 报错）才回退为重新 spawn 全新子代理，并按既有增量语义携带上一轮全部 Critical 逐字原文与路径清单。

备选方案是维持"每轮重新 spawn"。它的好处是每轮上下文干净、不受上一轮判断影响（抗锚定）、成本可预测；代价是每轮冷启动加全量重读文件。审查场景要读的文件多，复用通常更省，而且能顺手省掉"逐字携带上一轮 Critical 原文 + 路径清单"这套传递机制的构造成本。抗锚定的需求在"子代理给出明显错误判断"时仍然重要，保留"重新 spawn"作为显式回退即可。

### 5. 慢验证移到归档前，review 只保留结构校验

`openspec validate` 是结构校验，很快，保留在 review-plan 每轮——修复 delta spec 后确实可能把结构改坏。

测试 / 类型检查 / 构建是慢验证，改为由新的 `archive-verification-gate` 在 `@lyx-archive` 委托归档前执行一次。备选方案是"中间轮只跑受影响测试、清零轮跑完整验证"，但项目并未提供可靠的"受影响测试"映射，维护映射的成本高于收益。

### 6. 移除弃用字段，而不是继续保留

`reviewModelB` / `reviewReasoningEffortB` 从类型定义、配置读写、init / menu 保留逻辑、doctor 提示中一并移除。既然本次已经确立破坏性变更，继续背着"字段保留但不读取"的负担只会让配置语义更模糊。

### 7. spec 采用 ADDED + 覆盖声明，而不是逐条 MODIFIED

`ly-review-gates` 有 11 个 Requirement，其中 10 个以"spawn 审查 subagent"为前提；`ly-propose-flow` 同理。逐条 MODIFIED 需要完整复制每个 Requirement 的全部场景，delta 体积会数倍于本次实际语义变化。

本次改为在每个受影响能力里 ADDED 一条"执行者可切换"的 Requirement，并在正文开头写明适用范围覆盖：原有以 spawn 为前提的 Requirement 只在执行者为 `"subagent"` 时适用，执行者为 `"main"` 时以新增 Requirement 为准。

这是一个显式的可读性折中：覆盖规则集中在新增 Requirement 的开头，读者不必在两个 Requirement 之间反复比对。代价是原有 Requirement 的措辞在新路径下需要依赖覆盖声明才能正确解读，审查者需要确认覆盖规则本身没有漏洞。

## Risks / Trade-offs

- **默认 main 削弱审查独立性** → 需要独立视角的用户必须显式配置 `reviewExecutor = "subagent"`；`lycx doctor` 展示当前执行者，向导明确展示"spawn 独立子代理"这一选项及其含义。
- **main 路径的"自己审自己"可能放过问题** → 保留 Critical / Warning / Info 分级输出与最多 2 轮自查；对高风险改动，用户可切回 subagent 路径。这是明示的取舍，不是遗漏。
- **复用子代理带来锚定效应** → 子代理可能延续第一轮的误判；复用失败自动重新 spawn，需要完全独立视角时也可手动触发重新 spawn。
- **验证后移出现"带病窗口"** → 从 review 清零到归档之间，代码可能处于未验证状态；归档前关卡是唯一兜底，若那时才失败，回修成本高于中途发现。
- **ADDED + 覆盖声明降低 spec 可读性** → 覆盖规则写在新增 Requirement 开头并逐条点名受影响的 Requirement 标题；审查阶段应重点核对覆盖规则是否有遗漏。
- **spawn 可用性不可靠** → 不做预探测，首次 spawn 失败即按环境级不可用回退 main 路径并输出 `[回退] subagent 不可用: <原始报错>`，流程不中断。

## Migration Plan

1. **配置**：升级后 `[codexHost]` 的 `reviewExecutor` / `codingExecutor` 视为未配置，等价 `main`。依赖独立审查或独立实施的用户需显式写入 `reviewExecutor = "subagent"` / `codingExecutor = "subagent"`。
2. **字段清理**：`reviewModelB` / `reviewReasoningEffortB` 不再被读取或保留写回。存量配置中的这两个键可由用户自行删除；`lycx doctor` 会提示该字段已移除。
3. **文档**：`README.md`、`CLAUDE.md`、`AGENTS.md`、`templates/CLAUDE.md` 同步更新执行者语义与验证时机；`workflow.md` 重写为单审 / 可切换执行者的流程图，清理其中过时的 `codex exec` 双审查内容。
4. **回滚**：若需回退，恢复上一版本的 skills 与角色词并重新 `lycx init --force`；配置中新增的执行者字段对旧版本是未知键，旧版本会忽略它们。
